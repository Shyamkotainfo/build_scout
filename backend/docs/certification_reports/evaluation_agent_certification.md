# EvaluationAgent Certification

## Current Architecture
The EvaluationAgent evaluates candidates generated by the ResearchAgent against component requirements. It executes `security.get` and `license.get` tools to fetch evidence, injects this into the LLM context, and evaluates candidates using 6 dimensions (relevance, compatibility, project health, license, security, maintainability). 

## Actual Execution Flow
1. Receives candidates from `BuildSmartState`.
2. Loops through each candidate, calling the `UnifiedToolGateway` for `security.get` and `license.get` via LOCAL providers using the candidate's URL/name.
3. Appends the fetched `security_evidence` and `license_evidence` to the candidate payload.
4. Serializes the entire block to JSON, enforcing a context compaction loop.
5. Invokes the LLM using `ainvoke_with_retry` and the `RawEvaluationsResponse` Pydantic model for self-healing JSON validation.
6. Enriches the response with a deterministic `overall_score` based on standard heuristics and saves it to state.

## Responsibilities
- **ResearchAgent** Discovers.
- **EvaluationAgent** Assesses via rigorous evidence-backed checks.
- **DecisionAgent** Decides (REUSE/ADAPT/BUILD). 

## Evaluation Dimensions
1. **Relevance Fit**: Does the candidate satisfy the requirement?
2. **Technical Compatibility**: Does it fit the requested ecosystem?
3. **Project Health**: Repository activity and community signals.
4. **License**: Permissive vs restrictive vs unknown (derived from explicit evidence).
5. **Security**: Audit history and vulnerability data (derived from explicit evidence).
6. **Maintainability**: Code ecosystem complexity.

## Scoring Model
Each dimension is scored 0-100 by the LLM based *only* on factual evidence. If evidence is missing (e.g. no security scan found), the LLM must output `null`. 
The `overall_score` is deterministically computed in Python using the weights:
- `relevance_score`: 25%
- `compatibility_score`: 20%
- `project_health_score`: 15%
- `license_score`: 10%
- `security_score`: 15%
- `maintainability_score`: 15%
If a dimension is `null` (missing evidence), the deterministic normalizer ignores it and dynamically adjusts the weights among the remaining known dimensions.

## Evidence Model
The LLM now strictly distinguishes between FACT and MISSING EVIDENCE. In the V1 test, when given `user-auth-service`, the LLM stated:
```json
"reasoning": "Candidate directly implements JWT and OAuth 2.0 authentication with login... No license or security evidence provided.",
"concerns": [
  "Last code push significantly outdated (2024-08-23)...",
  "No security audit evidence or known vulnerability disclosure provided",
  "License information completely absent"
],
"missing_evidence": [
  "License type and restrictions",
  "Security audit history or vulnerability disclosures"
]
```

## Issues Found
1. Original EvaluationAgent didn't execute `security.get` or `license.get`. The ResearchAgent blindly executed it on generic component names, yielding useless metadata.
2. Original `RawEvaluationResult` failed to map to `schemas.py` `EvaluationResponse` (e.g., output `candidate_id` instead of `candidate_name`, squashed scores into a single LLM output, and lacked reasoning).
3. Parsing validation occurred outside the retry loop, risking hard crashes.

## Fixes Applied
1. `UnifiedToolGateway` introduced to EvaluationAgent to fetch per-candidate metadata.
2. Refactored `EvaluationResponse` schema to support multi-dimensional deterministic scoring alongside rigorous LLM reasoning arrays.
3. Centralized JSON validation using `response_model` inside `ainvoke_with_retry` in `retry.py`.
